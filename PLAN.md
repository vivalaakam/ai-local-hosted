# План: локальный AI-шлюз и GPUI-чат

Дата: 2026-11-08. Репозиторий пустой, кроме `references/`. Код пишем сами на Rust. Каталог `references/` только для чтения.

## Цель

Один локальный сервер, к которому ходят два типа клиентов.

1. Кодовые агенты шлют запрос на наш API. Cursor, Cline, Aider и OpenCode говорят на Chat Completions. Codex говорит на Responses API. Claude Code говорит на Anthropic Messages. Сервер переводит каждый из этих входов в один внутренний запрос и выбирает провайдера. Первый провайдер — Ollama. Тот же адаптер потом принимает любой OpenAI-совместимый endpoint: LM Studio, vLLM, OpenAI, OpenRouter, Groq.
2. Приложение на GPUI ходит в API чатов этого же сервера. Сервер хранит диалоги в PostgreSQL и стримит ответ модели.

Сервер — единственная точка, которая знает провайдеров и хранит чаты. Десктоп не вызывает Ollama напрямую.

## Решения, от которых уже отталкиваемся

Если какое-то решение неверное, его дешевле поменять до фазы 1.

| Тема | Решение |
| --- | --- |
| Вход для агентов | Три протокола на одном внутреннем запросе. `POST /v1/chat/completions` и `GET /v1/models`. `POST /v1/responses` для Codex. `POST /v1/messages` для Claude Code. Везде стриминг и проброс инструментов. |
| Вход для чата | Отдельный `/api/conversations`. История живёт в Postgres. Ответ той же SSE-формой, что и у агентов. |
| Что писать в базу из агентского вызова | В `request_log` только метаданные: клиентская модель, upstream-модель, провайдер, статус, латентность, токены. Полный промпт в лог не пишем. Исключение — таблица `response_states`: Responses API хранит состояние хода 7 дней, иначе `previous_response_id` у Codex не работает. Это не лента чата. |
| Маршрут модели | Провайдер по умолчанию — голым именем модели. Явный выбор: `{uuid}::qwen2.5-coder:7b` (двойное двоеточие, uuid провайдера). Одинарное двоеточие остаётся тегом Ollama. Заголовок `X-Provider` тоже выбирает провайдера и тоже равен его uuid. |
| Пользователи | У каждого свои чаты и провайдеры. Вход — пароль через `POST /oauth/register` и `POST /oauth/token`. Access-токен живёт около 30 дней, refresh около 90 и сменяется при использовании. |
| Секреты провайдеров | Токен upstream лежит в `providers.token` и принадлежит пользователю. Ответы API и логи отдают только `has_token`. Пароль на сервере — argon2. В Postgres лежат sha256-хеши токенов сессии, не сами токены. |
| Десктоп и SQLite | URL сервера, сессия входа, черновик ввода, кэш списка чатов. Источник правды по сообщениям — Postgres на сервере. Keyring не используем. Токен провайдера в SQLite не пишем. |
| UI-стек | `gpui-kit`, как у Magenta: версия закреплена, серверные крейты от GPUI не зависят. Первое действие фазы 7 — пустое окно на macOS. Если не соберётся, переключаемся на связку `gpui` + `gpui-component` до написания экранов. |
| Язык кода | Идентификаторы, комментарии и коммиты на английском. Документы плана и `AGENTS.md` на русском. |
| Имена | Крейты `alh-core`, `alh-providers`, `alh-storage`, `alh-server`, `alh-desktop`. Бинарники `alh-server` и `alh-chat`. |
| ORM | SeaORM 2 поверх Postgres. Сложный SQL идёт через `ConnectionTrait`, без макросов `query!`. Миграции — файлы в `migrations/`, учёт в таблице `alh_migrations`. |
| Лицензия нашего кода | [PolyForm Noncommercial 1.0.0](LICENSE). Бесплатно для некоммерческого использования, личных проектов, учёбы и некоммерческих организаций. Коммерческое использование эта лицензия не разрешает. Чужой AGPL-код не переносим. |

Локальная база для разработки и интеграционных тестов:

```text
postgres://local_user:local_password@localhost:15432/ai-local-hosted
```

Сервер слушает `127.0.0.1:8080`. Ollama ожидается на `http://127.0.0.1:11434`, OpenAI-совместимый префикс — `http://127.0.0.1:11434/v1`.

## Что остаётся за первой версией

Эти вещи есть в референсах и сюда не входят, пока не закрыты фазы 1–7.

- Каталог из десятков бесплатных провайдеров, bandit, квоты RPM/TPM, fusion-модели. Это продукт FreeLLMAPI, не наш.
- Нативные адаптеры Anthropic и Gemini как upstream. Строку с `protocol = anthropic` можно сохранить, но вызов этого провайдера отвечает ошибкой, пока нет отдельного адаптера. Claude Code и Codex по-прежнему приходят своими протоколами на вход и уходят в OpenAI-совместимый upstream.
- Биллинг, внешний IdP, админка. Свои пользователи и парольный OAuth уже есть.
- Эмбеддинги, RAG, память, агентский цикл, инструменты на стороне сервера, computer use, глубокий ресёрч.
- Генерация картинок, речи, видео.
- Рабочая область с git, диффами и песочницей. Magenta и Leon это умеют. Наш GPUI в v1 — чат.
- Встроенный Postgres в десктопе. У ChatGPUI так сделано. У нас Postgres уже внешний.

## Что брать из каждого референса

### Magenta — каркас, который нам ближе всего

Rust, GPUI через `gpui-kit` 0.6.1, edition 2024, тулчейн CI — Rust 1.98. Крейты: `core` без HTTP, SQLite и GPUI; `application` со сценариями; `providers` с проводами; `storage`; `ui`; `desktop` только склеивает.

Полезные контракты из `references/magenta/crates/core`:

- `ChatProvider::stream` возвращает поток `GenerationEvent`. Отмена — это drop потока, а не отдельный флаг.
- События: старт, текстовая дельта, завершение с `finish_reason` и usage, либо типизированная ошибка.
- Перед вызовом модели хранилище в одной транзакции пишет сообщение пользователя и плейсхолдер ассистента со статусом streaming. Токены в SQLite по одному не пишутся. В конце одна финальная запись. После падения процесса зависший streaming становится остановленным.
- `select_context` режет историю целыми ходами пользователя, а не обрывком сообщения. В v1 достаточно простого лимита по последним сообщениям. Сам приём «не рвать ход» оставляем в типе контекста.
- Настройки окна не лежат в базе чатов. Сессия десктопа лежит в его SQLite, токен провайдера остаётся на сервере.

Не берём: агента с файлами и git, ChatGPT OAuth, Bubblewrap, локальную SQLite как источник чатов, demo-провайдер как продуктовую функцию. Демо-провайдер можно оставить тестовым двойником внутри `alh-providers`.

### ChatGPUI — как выглядит нативный чат

GPUI из git Zed, `gpui-component`, nightly `nightly-2026-01-18`. Один бинарь, модули `llm`, `chat`, `database`, `settings`. Провайдер — трейт `LlmProvider` со `stream_chat` в `async_channel`. SeaORM, сущности `conversations`, `messages`, `attachments`. У сообщения роль, статус `pending | streaming | done | error`, текст и отдельно thinking. Стрим в UI debounce около 50 мс. Списки виртуализированы. Смена провайдера и выбор чата идут событиями GPUI.

Не берём: встроенный Postgres, прямой вызов Anthropic/OpenAI из UI, AGPL-код, nightly, пока серверные крейты могут жить на stable.

Схема чата у них достаточная для v1, если добавить роли `tool`, `tool_calls` и порядковый номер сообщения. Thinking храним отдельным полем, даже если Ollama его пока не присылает.

### FreeLLMAPI — вход для кодовых агентов

Node-шлюз. Клиент видит один Bearer и OpenAI-совместимые пути. Адаптер провайдера: `chatCompletion` и `streamChatCompletion`. Роутер на каждый запрос выбирает живую модель, при 429/5xx идёт дальше по цепочке. Ключи шифруются, квоты лежат в SQLite. Есть ещё `/v1/responses`, `/v1/messages`, `/v1/embeddings`, нативный Gemini и Ollama. Чат как продукт они не хранят: это прокси.

Берём в первую поставку:

- пути `/v1/chat/completions`, `/v1/models`, `/v1/responses`, `/v1/messages`;
- стриминг `text/event-stream` в форме того протокола, которым пришёл клиент;
- проброс инструментов во всех трёх входах;
- перевод Anthropic и Responses во внутренний запрос, а не второй вызов модели;
- один адаптер на OpenAI-совместимый HTTP, параметризованный `base_url` и ключом;
- таймаут до первого байта и обрыв, если поток замолчал;
- классификацию ошибок: 401, 404 модели, 429, сеть, обрыв стрима. Код наружу — короткий, тело провайдера в ответ клиенту целиком не кладём.

Смотреть соответствие полей можно в `references/freellmapi/docs/en/architecture/03-streaming-pipeline.md`, разделы Anthropic Messages и Responses API Shim. Реализацию оттуда не переносим.

Не берём: bandit, 34 платформы, каталог с freellmapi.co, шифрование ключей, failover на 20 попыток, compression, MCP, десктоп-трей, Gemini `/v1beta`.

### LobeHub — как не раздуть схему

Postgres через Drizzle. Полезный минимум, который у них уже разъехался на десятки колонок:

- провайдер: id, имя, enabled, секрет отдельно от настроек, json настроек endpoint;
- модель: id внутри провайдера, тип `chat`, контекстное окно, abilities;
- сессия / топик — контейнер диалога;
- сообщение: роль, контент, модель, провайдер, usage, tools, reasoning, error, порядковая связь с топиком.

Их `messages` ещё несёт workspace, agent, thread, parent, group, quota, soft-delete. Это следы мультипользовательского продукта. В v1 сообщение принадлежит одному разговору и имеет `position`. Ветки сообщений и корзина не нужны.

Их разделение `ai_providers` / `ai_models` оставляем: список моделей Ollama приходит с `/api/tags` или `/v1/models` и кэшируется в таблице, а не зашивается в код.

### RikkaHub — настройки провайдера

Kotlin-модуль `ai/` отделён от Android UI. `Provider<Setting>` без состояния: `listModels`, `streamText`, `generateText`. Настройка — sealed class: OpenAI-совместимый (`baseUrl`, `apiKey`, путь chat completions), Claude, Google. Модели — список внутри настройки, не глобальный enum. Инструменты и usage входят в параметры генерации. Картинки и эмбеддинги у трейта есть, реализации по умолчанию отвечают «не поддерживается».

Берём stateless-адаптер и закрытый набор видов провайдера. В v1 вид один: `openai_compatible`. Методы картинок и эмбеддингов в трейт не добавляем, пока нет вызывающего кода.

### Khoj — серверный чат

Django, Postgres. `ChatModel` указывает тип провайдера и API endpoint. `Conversation` хранит ленту одним JSON-полем и валидирует её при сохранении. Удобно для прототипа и плохо для стрима: нельзя дописать статус одного сообщения, не переписав весь документ. Наш вариант — строки `messages`, как у ChatGPUI и LobeHub.

Полезное: чат на сервере привязан к модели, заголовок отделён от текста, клиент может быть разным при одной базе. Не берём поиск по документам, агентов, подписки и JSON-ленту.

### Leon — агент, который нам рано делать

Node, навыки, память в несколько слоёв, SQLite на профиль, цикл инструментов с журналом ходов. Полезные правила на будущее, не на v1:

- инструменты объявлены, а не спрятаны в свободный текст модели;
- большой вывод инструмента хранится отдельно, в контекст попадает укороченный вид;
- заголовок чата выводится отдельным коротким вызовом и не блокирует ответ;
- отмена не дописывает «успешный» финал.

В бэклог, не в фазы 1–7.

### deep-research — маленький цикл исследования

Меньше 500 строк. Ширина и глубина, параллельные поисковые запросы, затем markdown-отчёт. Модель берётся через OpenAI-совместимый endpoint, в том числе локальный. Когда шлюз уже стоит, такой цикл может стать отдельным бинарём `alh-research`, который ходит в наш `/v1`. В этот план реализации он не входит.

### Rivet — GPUI-оболочка

Rust Matrix-клиент: `rivet-core` (стор и клиент), `rivet-ui` (окно, сайдбар, таймлайн, ввод). Подтверждает, что чатовый лейаут на GPUI уже собирают из сайдбара и ленты. Протокол Matrix, E2EE и звонки нам не нужны.

## Архитектура

```text
кодовый агент                         GPUI alh-chat
      |                                    |
      |  /v1/chat/completions              |  /api/conversations
      |  /v1/responses                     |  SQLite: url, черновики
      |  /v1/messages                      |
      |  /v1/models                        |
      v                                    v
                    alh-server (axum)
                     |            |
                     |            +-- alh-storage --> PostgreSQL
                     v
                  alh-core
                маршрут, типы сообщения, трейт провайдера
                     |
                     v
               alh-providers
            OpenAI-compatible HTTP
                     |
                     +-- Ollama :11434/v1
                     +-- позже любой другой /v1
```

`alh-core` не зависит от axum, sqlx, sea-orm, reqwest и gpui. Сервер и провайдеры зависят от core. Десктоп не зависит от `alh-providers` и `alh-storage`.

Поток чата:

1. Клиент создаёт разговор или шлёт сообщение в существующий.
2. Сервер в одной транзакции пишет user-сообщение и пустое assistant-сообщение со статусом `streaming`.
3. Собирает контекст из сообщений этого разговора со статусом `done` плюс новое user-сообщение.
4. Резолвит провайдера и зовёт `ChatProvider::stream`.
5. Дельты уходят клиенту. В базу на каждую дельту не пишем.
6. Успех — одна запись: текст, usage, статус `done`. Обрыв клиента или ошибка — статус `cancelled` или `error`, уже полученный текст сохраняем.
7. При старте сервера все строки `streaming` старше этого процесса помечаются `error` с кодом `interrupted`.

Поток агента короче. Chat Completions, Responses и Anthropic Messages переводятся в один `CompletionRequest`. Тело в `request_log` не пишем. Резолвим модель, стримим upstream, наружу отдаём события в протоколе клиента. В конце — строка лога. Для `/v1/responses` дополнительно пишем `response_states`, чтобы следующий ход мог сослаться на `previous_response_id`.

Отмена агентского стрима — закрытие HTTP-тела. Upstream-запрос должен оборваться вместе с ним.

## Модель данных Postgres

Идентификаторы — UUID. Время — `timestamptz`. Порядок сообщений — `position int`, уникальный в паре с `conversation_id`.

`providers`

- `id` UUID, первичный ключ. Сервер выдаёт его при создании. Клиент id не присылает
- `protocol` — `openai` или `anthropic`. Написание `antropic` принимается на входе и сохраняется как `anthropic`
- `display_name`
- `url` — для `openai` уже с `/v1`
- `token` текст null — сам секрет upstream. Пусто для Ollama. В список и ответы API не попадает, снаружи только `has_token`
- `default_model` текст null — имя upstream-модели, если клиент прислал алиас или семейство
- `is_default` bool, истинно ровно у одного
- `enabled` bool

`models`

- `provider_id`, `name` — вместе уникальны. `name` — то, что уходит upstream (`qwen2.5-coder:7b`)
- `context_window` int null
- `supports_tools` bool
- `fetched_at`

`conversations`

- `id` uuid
- `title` текст, сначала пустой или первая строка пользователя, усечённая
- `provider_id`, `model`
- `system_prompt` текст null
- `created_at`, `updated_at`, `archived_at` null

`system_prompts`

- `user_id`, `scope` — первичный ключ. Служебный пользователь `00000000-0000-0000-0000-000000000001` может иметь только `scope = global`; у реального пользователя бывают `assigned` и `self`.
- `content`, `updated_at`
- На каждый запрос сервер добавляет непустые слои перед клиентскими системными сообщениями в порядке `global`, `assigned`, `self`. Оператор сервера задаёт `global` и `assigned` напрямую в БД; API пользователя читает и меняет только его `self`.

`messages`

- `id` uuid
- `conversation_id`
- `position`
- `role` — `system | user | assistant | tool`
- `content` текст
- `parts` jsonb null — исходные части, если контент был не строкой
- `tool_calls` jsonb null
- `tool_call_id` текст null
- `thinking` текст null
- `status` — `streaming | done | error | cancelled`
- `error_code` текст null
- `usage` jsonb null — `prompt_tokens`, `completion_tokens`
- `created_at`, `finished_at`

`request_log`

- `id` uuid
- `source` — `agent | chat`
- `protocol` — `chat_completions | responses | anthropic_messages | chat`
- `conversation_id` null
- `message_id` null — assistant-сообщение чата
- `provider_id`
- `client_model` — строка, которую прислал клиент
- `model` — имя, ушедшее upstream
- `status`, `error_code` null
- `latency_ms`, `prompt_tokens` null, `completion_tokens` null
- `created_at`

`response_states`

- `id` текст, первичный ключ, вид `resp_...`
- `previous_id` текст null
- `client_model`, `provider_id`, `upstream_model`
- `messages` jsonb — внутренний транскрипт после этого хода
- `output` jsonb — выходные элементы Responses API
- `created_at`

Строки старше 7 дней удаляются при старте сервера. В чаты они не попадают.

Индексы: сообщения по `(conversation_id, position)`, разговоры по `updated_at desc`, лог по `created_at desc`, `response_states` по `created_at`.

Пустая таблица `providers` при обычном запуске остаётся пустой: провайдера добавляет пользователь. `OLLAMA_BASE_URL` используется только когда `Config.seed` включён (так делают тесты): тогда в пустую таблицу пишется строка служебному пользователю, `id` — новый UUID, имя `Ollama`, `protocol = openai`, `url` с `/v1`, пустой `token`, `is_default = true`. Первая настоящая регистрация забирает эти строки себе.

SQLite десктопа, отдельный файл в каталоге данных приложения:

- `settings`: ключ/значение, как минимум `server_url`
- `session`: одна строка с именем, access-токеном, refresh-токеном и сроком access. Это сессия входа, не токен провайдера
- `drafts`: `conversation_id` или пустой ключ для нового чата, текст
- `conversation_cache`: id, title, updated_at, model. Кэш для быстрого открытия. После успешного `GET /api/conversations` перезаписывается. При расхождении побеждает сервер.

## HTTP

Аутентификация на всех путях, кроме `GET /health`, `POST /oauth/register` и `POST /oauth/token`. Заголовок `Authorization: Bearer` или `x-api-key` — access-токен пользователя. Сервер хранит sha256 этого токена и по нему находит пользователя. Общего секрета процесса нет, для старта хватает `DATABASE_URL`.

`POST /oauth/register` принимает JSON `{username, password}`, создаёт пользователя и сразу возвращает токены. `POST /oauth/token` принимает форму `grant_type=password` или `grant_type=refresh_token`. Ответ: `access_token`, `token_type: Bearer`, `expires_in`, `refresh_token`. Неверный пароль и неизвестное имя отвечают одинаково, кодом `invalid_grant`. Первый зарегистрированный пользователь забирает строки, которые остались у служебной учётки до появления аккаунтов. Саму служебную учётку не удаляем.

`GET /health` без секретов в теле: `ok`, если Postgres отвечает, и `provider: unknown`. Анонимный health не смотрит провайдеров пользователя.

`GET/POST /api/providers` и `PATCH/DELETE /api/providers/{id}` под тем же bearer, что и остальной API. `id` в пути — UUID. Тело создания: `display_name`, `protocol`, `url`, необязательные `token`, `default_model`, `is_default`, `enabled`. Сервер сам ставит `id`. В ответах токена нет, только `has_token`. `PATCH` отличает пропуск поля от `null`: `null` очищает `token` и `default_model`. Удаление провайдера, на который ссылается разговор, — 409.

`GET /v1/models` — список из таблицы `models` в форме OpenAI: `object: list`, элементы `id`. Идентификатор для клиента: голый `name`, если провайдер дефолтный, и `{uuid}::name` для явного выбора. Перед ответом сервер может обновить список у дефолтного провайдера, если кэш старше нескольких минут. Ошибка обновления отдаёт прошлый кэш.

`POST /v1/chat/completions`

Принимаем поля, без которых агенты не работают: `model`, `messages`, `stream`, `tools`, `tool_choice`, `temperature`, `top_p`, `max_tokens` / `max_completion_tokens`, `stop`. Лишние неизвестные поля не валят запрос. `stream: false` собирает ответ целиком. `stream: true` или отсутствие поля при типичном агентском клиенте — по спецификации OpenAI отсутствие означает false. Делаем как в спецификации: стрим только при `stream: true`.

Сообщение: `role`, `content` строка или массив частей, `name`, `tool_calls`, `tool_call_id`. Части, которые не понимаем, передаём upstream как есть, если это JSON-объект OpenAI. Отказываемся только от явно битого тела.

Ответ нестриминговый — обычный `chat.completion`. Стрим — `chat.completion.chunk`. Финальный usage, если upstream его прислал, уходит в последнем чанке и в `request_log`. Поле `model` в ответе повторяет модель из запроса клиента, даже если upstream был другим. В логе остаются оба имени.

Резолв модели, общий для всех входов:

1. `{uuid}::name`, если этот провайдер есть у пользователя и имя есть в его каталоге.
2. Голое имя в каталоге дефолтного провайдера.
3. Точный алиас из `config/model-aliases.toml`.
4. Префикс из того же файла. В поставке префиксы `claude-`, `gpt-`, `o1`, `o3`, `o4`, `codex-` ведут на `providers.default_model` дефолтного провайдера.
5. Иначе `model_not_found`.

Так Claude Code может слать `claude-sonnet-4-5`, а Codex — имя семейства GPT, и оба попадут в выбранную модель Ollama. Опечатка вроде `qwen-nope` остаётся ошибкой.

`POST /v1/responses`

Вход Codex. Тело переводится во внутренний запрос и обратно. Поддерживаем `model`, `instructions`, `input` строкой или массивом элементов `message`, `function_call`, `function_call_output`, `tools`, `tool_choice`, `stream`, `temperature`, `max_output_tokens`, `previous_response_id`. Неизвестные поля не валят запрос. Картинки во входе в этой фазе не обещаем: текстовые части проходят, нетекстовые без текста дают `invalid_request`.

Если есть `previous_response_id`, сервер берёт сохранённый транскрипт и добавляет новые входные элементы. Нет сохранённого id — `not_found`. Состояние пишется на каждый успешный и оборванный ход, в том числе при `store: false`: локальному Codex нужна цепочка, а не политика хранения OpenAI.

Нестриминговый ответ — объект `response` с `output_text` и `output`. Стрим отдаёт как минимум `response.created`, `response.output_item.added`, `response.output_text.delta`, `response.function_call_arguments.delta`, `response.output_item.done`, `response.completed`. Ошибка после начала потока — событие `error` и конец потока.

`POST /v1/messages`

Вход Claude Code. Клиент ходит на origin сервера и сам дописывает `/v1/messages`. Аутентификация: `Authorization: Bearer` или `x-api-key` с access-токеном пользователя. Заголовок `anthropic-version` принимается и не проверяется на конкретную дату.

Поддерживаем `model`, `max_tokens`, `system` строкой или блоками, `messages` с ролями `user` и `assistant`, контент строкой или блоками `text`, `tool_use`, `tool_result`, плюс `tools`, `tool_choice`, `stream`, `temperature`, `top_p`, `stop_sequences`. Блоки `thinking` на входе принимаем как текст рассуждения и во внутренний запрос кладём отдельно от ответа. Картинки и документы в этой фазе не обещаем.

Перевод: `system` становится системным сообщением, `tool_use` — `tool_calls`, `tool_result` — роль `tool`, `stop_reason: tool_use` соответствует завершению с вызовом инструмента.

Нестриминговый ответ — объект `message`. Стрим: `message_start`, `content_block_start`, `content_block_delta`, `content_block_stop`, `message_delta`, `message_stop`. Ошибки — тип Anthropic: `authentication_error`, `invalid_request_error`, `not_found_error`, `overloaded_error`, `api_error`.

`POST /v1/messages/count_tokens` возвращает грубую оценку, байты UTF-8 поделённые на 4, вместе со схемами инструментов. Это нужно, чтобы Claude Code не падал на подсчёте окна. Настоящий токенизатор модели не подключаем.

`GET /v1/models` при заголовке `anthropic-version` отдаёт список в форме Anthropic: наши модели плюс алиасы. Без заголовка остаётся форма OpenAI.

`GET /api/conversations?limit&cursor` — список без тел сообщений: id, title, model, provider_id, updated_at.

`POST /api/conversations` — `{ title?, model?, provider_id?, system_prompt? }`. Пустая модель значит дефолтный провайдер и модель, которую он отдаёт первой, либо заголовок запроса позже на сообщении.

`GET /api/conversations/:id` — разговор и сообщения по `position`.

`PATCH /api/conversations/:id` — title, model, system_prompt, archived.

`DELETE /api/conversations/:id` — удаляет разговор и сообщения.

`GET /api/system-prompt` возвращает собственный слой текущего пользователя. `PUT /api/system-prompt` принимает `{ content: string | null }`: строка записывает `self`, `null` или пустая строка его удаляет. Глобальный и назначенный слои этим API недоступны.

`POST /api/conversations/:id/messages`

Тело: `{ content: string, model?: string }`. Сервер добавляет ход, стримит SSE в формате chat completion chunk. Заголовки ответа: `X-Conversation-Id`, `X-Message-Id` (id плейсхолдера ассистента). Клиент рисует дельты и по концу помечает сообщение готовым. Повторная загрузка `GET` показывает уже сохранённый текст, даже если сокет оборвался на последнем чанке.

Ошибки API — JSON `{ "error": { "code", "message" } }`. Коды: `unauthorized`, `not_found`, `provider_unreachable`, `model_not_found`, `upstream`, `interrupted`.

## Провайдер

Трейт в `alh-core`, реализация в `alh-providers`.

```rust
trait ChatProvider: Send + Sync {
    fn id(&self) -> &str;
    fn list_models(&self) -> BoxFuture<Result<Vec<ModelDescriptor>, ProviderError>>;
    fn stream(&self, request: CompletionRequest) -> CompletionStream;
}
```

`CompletionStream` — `Pin<Box<dyn Stream<Item = Result<CompletionEvent, ProviderError>> + Send>>`.

`CompletionEvent`: `Delta(text)`, `ThinkingDelta(text)`, `ToolCallDelta { index, id, name, arguments }`, `Done { finish_reason, usage }`.

`ProviderError` несёт вид (`auth`, `not_found`, `rate_limited`, `unavailable`, `timeout`, `decode`, `cancelled`) и короткий безопасный текст. Сырой body в тип можно положить только под полем, которое сервер пишет в лог и не сериализует клиенту.

Реализация `OpenAiCompatibleProvider` ходит в `{base_url}/chat/completions` и `{base_url}/models`. Для Ollama `base_url` = `http://127.0.0.1:11434/v1`. Отдельный клиент нативного `/api/chat` не пишем, пока OpenAI-слой Ollama закрывает стрим, tools и список моделей.

Разбор SSE — свой небольшой парсер кадров `data:`. Зависимость ради одного формата не тащим. Таймаут до заголовков и тишина в потоке задаются константами в адаптере, с возможностью переопределить в конфиге.

Контрактный тест гоняет один и тот же набор запросов через `wiremock` или локальный `axum`-стаб: обычный текст, стрим из двух дельт, tool call, 404, оборванный SSE, обрыв читателя. Стаб не является Ollama. Живой Ollama — ручная проверка в фазе 4, не условие `cargo test`.

Второй OpenAI-совместимый провайдер — это вторая строка с `protocol = openai`, своим `url` и `token`, без нового Rust-типа. `protocol = anthropic` сохраняется, но вызов идёт в ошибку `invalid_request`, пока нет нативного адаптера.

## GPUI

Окно: слева список чатов, справа лента и поле ввода. Пока в SQLite нет сессии, вместо этого окно целиком показывает вход. Кнопка Settings внизу списка открывает отдельный экран вместо ленты: URL сервера, выход, access-токен и список провайдеров. Поля провайдера — в модальном окне. Модель выбирается над лентой и появляется только после того, как на этом экране есть провайдер. Тёмная и светлая тема на токенах gpui-kit, без копирования JSON-тем ChatGPUI.

Поведение v1:

- при старте читает `server_url` и сессию из SQLite. Нет сессии — экран входа. Просроченный access обновляется через refresh. Не вышло — снова экран входа;
- кнопка Settings внизу списка открывает отдельный экран. Там URL сервера, выход, access-токен для кодового агента и список провайдеров с кнопкой «Add provider». Имя, URL, токен и протокол вводятся в модальном окне; поле id нет, сервер выдаёт UUID. Токен провайдера в поле обратно не подставляется; пустое поле при правке оставляет сохранённый секрет. Смена URL сервера стирает сессию. Chat или выбор чата возвращает ленту;
- выбор чата грузит сообщения;
- отправка пишет черновик в SQLite сразу и чистит его после принятия сервером;
- стрим батчится примерно раз в 50 мс, чтобы не перерисовывать глиф на каждый токен;
- кнопка Stop рвёт HTTP и оставляет на экране уже пришедший текст; сервер сам пометит `cancelled`;
- ошибка провайдера остаётся в ленте, ввод не пропадает;
- смена модели патчит разговор и действует на следующие ходы;
- Markdown и подсветка кода — после того, как обычный текст уже стримится. До этого моноширинные блоки можно показать как текст.

Вне v1 десктопа: вложения, несколько окон настроек, виртуальный список на десятки тысяч сообщений, i18n, системное меню «о программе». Виртуальный список добавляем, когда обычная лента заметно тормозит.

Сеть из GPUI идёт через отдельную tokio-задачу. UI держит handle стрима и при закрытии вью его drop-ает.

## Крейты

```text
Cargo.toml                  workspace, resolver 2, edition 2024
crates/core                 типы, трейт, резолв `slug::model`, сбор контекста
crates/providers            OpenAI-compatible HTTP
crates/storage              миграции и репозитории Postgres, SeaORM
apps/server                 бинарь alh-server, axum, конфиг
apps/desktop                бинарь alh-chat, gpui-kit, SQLite, HTTP-клиент
migrations                  SQL, подключается из alh-storage
```

Серверные крейты собираются без gpui. `cargo test --workspace --exclude alh-desktop` обязан проходить на машине без дисплея. Десктоп исключаем из этой команды только если gpui-kit не линкуется в CI. Локально на macOS он входит в проверку фазы 6.

Конфиг сервера, переменные:

- `DATABASE_URL` — обязательна
- `BIND` — по умолчанию `127.0.0.1:8080`
- `OLLAMA_BASE_URL` — по умолчанию `http://127.0.0.1:11434`, только для тестового сида
- `PROVIDER_TIMEOUT_MS`, `STREAM_IDLE_MS` — необязательны

Файл `.env` в git не коммитим. Пример — `.env.example` без секретов, токен там placeholder. Бинарь `alh-server` читает `.env` из текущего каталога или родителей через dotenvy до старта runtime и не перезаписывает переменные, которые уже заданы в окружении. Нет файла — это не ошибка. Битый файл останавливает запуск.

## Фазы

Каждая фаза заканчивается проверяемым состоянием. Следующую не начинаем, пока предыдущая не зелёная. Новые зависимости — через `cargo add` и только после согласия. Релизные сборки не делаем.

### Фаза 1. Каркас и домен

Состав: workspace, `alh-core`, пустые заглушки остальных крейтов чтобы граф зависимостей был виден, `.env.example`, `.gitignore` для `target/`, `.env`, баз SQLite.

В core: роли, статусы, `CompletionRequest`, события, ошибки провайдера, разбор идентификатора модели, выбор провайдера по умолчанию, сборка контекста из списка сообщений с лимитом по числу последних ходов.

Готово, когда `cargo test -p alh-core` покрывает разбор `slug::name`, отказ от неизвестного слага, дефолтный маршрут и то, что системный промпт разговора попадает в контекст один раз.

### Фаза 2. Адаптер Ollama / OpenAI-compatible

Состав: `alh-providers`, стаб HTTP в тестах, разбор SSE.

Готово, когда контрактные тесты из раздела «Провайдер» зелёные и адаптер не тянет gpui, sqlx и sea-orm.

### Фаза 3. PostgreSQL

Состав: миграции, репозитории провайдеров, моделей, разговоров, сообщений, лога. Сид Ollama. При открытии пула — перевод зависших `streaming` в `error`.

Готово, когда тест против `DATABASE_URL` создаёт разговор, пишет user + streaming assistant одной транзакцией, финализирует assistant и читает ленту по порядку. Тест обязан откатывать свои строки или работать в транзакции, которая не коммитится. Чужие данные в базе не трогаем. Если `DATABASE_URL` не задан, этот тест запускается отдельным бинарём и явно падает с текстом, какой URL ожидается. Обычный `cargo test -p alh-core -p alh-providers` базу не требует.

### Фаза 4. API агентов

Состав: axum, health, models, chat completions, лог без тела промпта, Bearer.

Готово, когда curl против поднятого сервера и тестового стаба вместо Ollama показывает:

- 401 без токена;
- список моделей;
- нестриминговый ответ;
- стрим с `[DONE]`;
- проброс tool call туда и обратно;
- строку в `request_log` без текста сообщений.

Ручная проверка с живой Ollama записывается в комментарий к фазе: модель, команда, что ответ пришёл. Это не замена теста со стабом.

### Фаза 5. API чатов

Состав: CRUD разговоров и `POST .../messages` со стримом и сохранением.

Готово, когда интеграционный тест делает два хода, рвёт третий на середине и после нового чтения видит сохранённый префикс со статусом `cancelled` или `error`. Параллельный второй стрим в тот же разговор отклоняется: один активный assistant на разговор.

### Фаза 6. Responses и Anthropic Messages

Состав: чистый перевод в `alh-core`, маршруты в `alh-server`, таблица `response_states`, файл `config/model-aliases.toml`. Upstream остаётся тем же OpenAI-совместимым адаптером. Новый провайдер не появляется.

Готово, когда тесты на стабе, без живой Ollama, показывают:

- Codex-подобный `POST /v1/responses`: текст, стрим `output_text.delta`, вызов функции и `previous_response_id`, который продолжает ход без повторной отправки старых элементов;
- Claude Code-подобный `POST /v1/messages`: Bearer и `x-api-key`, системный промпт, стрим до `message_stop`, блок `tool_use` туда и обратно;
- имя `claude-sonnet-4-5` уходит в `default_model`, а в ответе клиенту остаётся `claude-sonnet-4-5`;
- неизвестное имя вне алиасов даёт `model_not_found`;
- `count_tokens` возвращает число;
- в `request_log` нет текста сообщений, в `response_states` транскрипт есть только у Responses.

Ручная проверка: Claude Code с `ANTHROPIC_BASE_URL=http://127.0.0.1:8080` и `ANTHROPIC_AUTH_TOKEN`, Codex с `wire_api = "responses"` и base URL `http://127.0.0.1:8080/v1`. Оба должны получить ответ Ollama и совершить один ход с инструментом. Это дополнение к тестам на стабе, не замена.

### Фаза 7. GPUI

Сначала пустое окно `alh-chat` на macOS. Если `gpui-kit` не собирается, фиксируем это в `PLAN.md` и переключаем UI-крейт на связку, которой пользуется ChatGPUI, не меняя сервер.

Дальше экраны из раздела «GPUI». Проверка руками по списку: сервер запущен, Ollama отвечает, создать чат, отправить сообщение, увидеть стрим, остановить, перезапустить приложение, увидеть тот же текст с сервера, сменить модель, удалить чат. Черновик переживает перезапуск, пока сообщение не отправлено. Скриншот без этого сценария фазу не закрывает.

Автотест десктопа в v1 — на чистую логику батчинга дельт и состояния ленты, без GPU. Смок окна — ручной.

## Бэклог после фазы 7

Порядок, если не скажут иной:

1. Второй реальный endpoint одной строкой конфига, без нового кода адаптера. Проверяет, что Ollama не зашита.
2. Картинки во входе Responses и Anthropic, когда модель Ollama их правда принимает.
3. Заголовок чата отдельным коротким вызовом модели.
4. Нативный upstream-адаптер только для протокола, который не притворяется OpenAI.
